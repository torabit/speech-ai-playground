### わかったこと

#### 遅延は「何から何まで」を決めないと測れない

同じ「遅れ」に見えて、別のものを測る 2 つの式がある。

- 送信ペースのずれ → いまの時刻 − 送った音声の長さ
- 認識の遅れ → 結果が届いた時刻 − その結果の最後の単語を話し終えた時刻

前者は実時間で送っていれば 0 付近に貼りつく。0 だから速いのではなくて、速さを見てない。ただし値が増えたら音声の転送が滞っているということなので、これ自体に使い道はある。

知りたいのは「話してから画面に出るまで」なので後者。こっちは単語の時刻が要る。

#### 遅延の原点をどこに置くか

- 最初は WebSocket が開いた時刻を原点にしてた
- ブラウザは接続を開いてからマイクを取るので、マイクの許可ダイアログを待った時間まで遅延に入る
- 最初のフレームが届いた時刻を原点にした

#### 遅延の内訳

- 話してから partial が出るまでが 200〜600ms。転送と認識の分
- 確定はそこからさらに 0〜1.2s。endpointing=300 の無音判定を待つので、文末の間の長さで振れる
- utterance_end は最後の単語から 1.2〜2.6s。endpointing 300ms + utterance_end_ms 1000ms とだいたい合う。ただし 3 件しか観測してない
- ブラウザ経由でどれだけ増えるかは分からなかった。11 秒の録音を localhost から流すと p50 416ms（4 件）、ブラウザ経由は 268 / 566 / 799ms（3 件）。件数が少なくて、文末の間の振れに埋もれてる
- 20ms ごとに送ってるフレームの到着間隔は p50 12ms / p95 31ms と揺れてた。まとめて届く分が乗ってるのかな？

#### 実時間で送るには絶対時刻に合わせる

- 1 フレーム送って `setTimeout(20)` で待つループだと、20ms ぴったりには起きないので誤差が積み上がる
- 44 秒流すと数百 ms ずれて、測りたい遅延がそのずれに埋もれる
- 次に送る時刻を「それまでに送った音声の長さ」から決めるようにしたら、44 秒で 0.1ms に収まった

#### 連続して話すと utterance_end はほとんど来ない

- 44 秒の録音で final は 10 回、utterance_end は 2 回だった
- speaking 表示は speech_started で on、utterance_end で off にしてるので、話し続けてる間は on に張りつく
- 区切りを見せたいなら speech_final のほうが素直。Phase 3 の割り込みをやるときに直す

## 20260919

- getUserMedia で 16000 指定して渡しても sampleRate は変わらないけれど、AudioContext で指定したら、ブラウザが 16kHz に落してた。

### わかったこと

#### サンプルレートとは

- 1秒間に音の波形を何回記録するかを表す値
- たとえば 16 kHz = 1秒間に16,000回、波形を記録する

#### 記録できる周波数には上限がある

- 高い音ほど、波形が1秒間に何度も速く上下する
- 波形を正しく記録するには、1周期あたり最低2回のサンプリングが必要
- そのため、16 kHzでサンプリングした場合、記録できる周波数の上限は 8 kHz
  - 16,000回/秒 ÷ 2 = 8,000周期/秒 = 8 kHz
- これは ナイキスト周波数と呼ばれる

#### 48 kHz → 16 kHz に落とすとき

- 単純に3回に1回だけデータを残すわけではない。

- 48 kHzの音声
  - 8 kHz以上の周波数成分をフィルターで除去
  - サンプルを間引く
  - 16 kHzの音声

先に8 kHz以上を削るのは、そのまま間引くと高い周波数が低い周波数として誤って記録される エイリアシングを防ぐため。

#### 声について重要なこと

ここで区別する必要があるのが、

- 声の高さ → 基本周波数がどのくらいか
- 声の聞き取りやすさ・音色 → どの周波数帯域まで含まれているか

という2つ。

つまり、「人の声自体はそれほど高い周波数ではない」からといって、高い周波数帯域が不要とは限らない。声の高さと、声を明瞭に聞き取るために必要な帯域は別の話。
